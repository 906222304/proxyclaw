# 关闭 TUN 后 TCP 零字节断流修复

本次修改基于 `fix/dns-proxy-lifecycle` 的 `0c0c25a`，保留此前 TCP 半关闭、SOCKS5 回复解析、UDP 生命周期和日志界面修复。

## 已验证的触发路径

2026-10-20 的定向复现中，同一 HTTPS 目标经 Meta 网卡成功，经 WLAN 时出现与原账户读取故障相同的现象：三次握手完成，SOCKS5 握手成功，本地监听端随后发送 RST，转发收发均为 0 字节，寿命约 12 ms。单独用同步回显服务也能复现，因此不是账户令牌或 Asio 特有问题；TCP 保活开、关均不改变结果。

对应复现连接的 WFP 事件为 `FWPM_NET_EVENT_TYPE_PUBLIC_CLASSIFY_DROP`，过滤器 ID `1574828`，层为 `FWPM_LAYER_STREAM_V4`，过滤器名为 `UniKNetWFP Stream Callout`；本机对应运行中的驱动为 `UniKNetWFPW864.sys`。这是对复现连接的直接证据，不能反推每一条历史账户请求都由同一过滤器丢弃。

旧的公网来源 Reflection 在物理网卡上与该流过滤路径存在兼容问题。测试没有停止或卸载驱动，也没有修改防火墙规则。

## 修改

- 应用到本地监听端改为本地地址转交：保留源地址和源端口，目的地址改为应用自己的本机地址，目的端口改为监听端口，按 outbound 注入。
- 网络过滤器只额外接收本地监听端发出的 loopback 回复，其他本地流量保持原有路径。
- 回复恢复原始远端地址和端口，并恢复原来捕获应用数据包的 `IfIdx/SubIfIdx`，不能使用 loopback 回复携带的网卡索引。
- SYN 停车注入器与普通网络工作线程共用相同的转换函数。端口复用发布新决策时清除旧的返回网卡信息，状态槽仍为 64 字节。
- 完整 MSVC GUI 构建还修正了原有 `HICON small` 与 Windows SDK 的 `small` 宏冲突，仅重命名该局部变量。

本次修改针对现有 IPv4 TCP 路径；UDP 和应用 IPv6 目的地址支持范围没有扩大。

## 验证及边界

1. `tests/test_tcp_redirect.cpp` 使用真实 WinDivert 用户态解析、过滤和校验和函数，验证物理/TUN 地址、返回网卡及子网卡、端口恢复、负载和校验和、端口复用、direct/不匹配流排除，以及 loopback 过滤边界。以 MSVC `/W4 /WX` 编译并通过，测试不打开驱动。
2. 临时隔离驱动实验只处理四个测试端口：旧公网来源 Reflection 的两条物理网卡回显连接失败；本地地址转交的四组回显（物理/TUN、保活开/关）全部通过。
3. 使用生产重定向函数及真实生产 SOCKS5 relay 的独立集成程序，限定四个测试端口、连接现有 `127.0.0.1:7890`。复核运行中，物理网卡与虚拟网卡各两次公开 HTTPS 请求全部 HTTP 200、证书验证通过。首次运行的四次中有一次虚拟网卡 TLS 超时，复核未重现；两轮的四次物理网卡请求均成功。
4. 修复分支原有 TCP 12 项回归通过。既有完整 TCP/UDP 测试在 IPv6 UDP 批量回收用例等待超时，不能宣称全部 23 项通过；本次未改动 UDP 实现。
5. 完整 Windows x64 Release GUI 程序构建成功。前端复用日志预览包中的既有构建，因为没有前端变更。

单连接强制使用 WLAN 能复现并验证本次触发路径，但整机 TUN 保持开启。当前正在运行的旧程序未替换；新包仍需在关闭 TUN、重启真实客户端的场景做最终验证。

开发环境运行新回归（Visual Studio 开发者终端，提供正常 WinDivert SDK）：

```powershell
python tests/run_tcp_redirect_tests.py --windivert-dir WinDivert-2.2.2-A/x64
```

## 本机启用

从托盘正常退出旧 ProxyClaw，等待它还原 DNS 后，再以管理员身份启动独立修复包。确认沿用原来的 ChatGPT.exe 子进程继承规则和 SOCKS5 127.0.0.1:7890，随后关闭 Clash TUN，重启客户端检查账户读取和对话。不能同时运行两个 ProxyClaw 实例。若失败，重新开启 TUN，并退出新包、恢复旧包；保留故障时间和两端日志。

不需要清理账户缓存，也不应为此卸载安全驱动。包内配置来自本机，只用于本机测试。
